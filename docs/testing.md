# Testing

## Running the suite

```sh
npm test        # single run
npm run test:watch   # watch mode
```

Vitest, `jsdom` environment. Test files are co-located with the source they test (`*.test.ts`/`*.test.mjs` next to the file it covers).

## Fixture-driven tests against the real WASM module

`src/wasm/bridge.test.ts` runs against the **real** `stage.wasm` module, not a mock — it reads `public/wasm/stage.wasm` + `wasm_exec.js` straight off disk via `node:fs` and injects them into the bridge's `fetchWasmExecSource`/`fetchWasmBytes` options, so no dev server or real network access is needed. Run `npm run wasm:download -- <version>` first if `public/wasm/` is empty (see `docs/development.md`).

A minimal `.def` fixture lives in `src/wasm/testdata/sample.def`, copied from the `stage` repo's own `cmd/wasm/testdata/sample.def` rather than depending on a sibling checkout at test time. Expected values in these tests were derived by running the real module once against the fixture, and by reading `stage`'s own parser source directly for behavior not obvious from the fixture alone — e.g. that a nil BG-element slice marshals to JSON `null` rather than `[]`, and that plain text with no recognizable section header parses successfully into an empty stage instead of erroring. Neither was assumed; both were confirmed against the real module's actual output.

The stage folder input (`src/input/stage-file-input.test.ts`, and `stage-file-input-view.test.ts`'s own end-to-end cases) also runs against the real `stage.wasm` module the same way, using the same fixture plus in-test `.sff` stand-ins (their content is never decoded by this item, so arbitrary bytes exercise name resolution and byte pass-through correctly).

`src/wasm/sff-bridge.test.ts` runs the same way against the real `sff.wasm` module (`public/wasm/sff/`, fetched via `npm run wasm:download:sff`), using a real `.sff` fixture (`src/wasm/testdata/v1-basic.sff`, copied from `lifebar-editor`'s own testdata) with one known sprite (group 0, image 0) — the exact metadata and pixel buffer size this fixture decodes to were obtained by running the actual module once, not derived from the mapping code under test. It also confirms a batch request mixing a present and an absent sprite reports a per-request error without failing the whole batch.

## Background preview

`background-composition.test.ts` exercises the pure composition logic (coordinate mapping, axis-offset placement, draw order, placeholder sizing, the parallax position formula, the time-based playback clock, and animation frame classification) against plain fixture data — no WASM, no DOM, no canvas needed, since none of it is involved in that layer. The playback clock is tested for its time-based (not callback-count-based) progression directly: many small steps summing to the same total elapsed time as one large step produce the same end state, and an oversized single step is clamped rather than let through. `resolveBgScale`/`buildDrawPlan`'s scaling (backlog item 009) is covered separately: a non-1.0 `xScale`/`yScale` scales an element's position, axis offset, and drawn size together; an unset (zero-value) scale falls back to `1`; and a stage with no scaling at all produces the exact same plan as before the fix.

`background-bounds.test.ts` (backlog item 012) exercises `computeStageBoundingBox`/`translateDrawCommands` the same way — plain fixture data, no WASM/DOM/canvas: byte-for-byte parity with the declared `localCoordWidth`/`Height` window when nothing exceeds it, per-axis expansion when a `DrawCommand`/`cameraBounds`/`stageBoundaries` value falls outside it, correct handling when `cameraBounds`/`stageBoundaries` are given out of their nominal `high`/`low`/`left`/`right` order, and outward rounding (`floor` on min edges, `ceil` on max edges) so a fractional edge never clips a pixel once the result feeds an integer canvas size.

`background-preview.test.ts` exercises the DOM/canvas orchestration on top, with the WASM bridge calls, the canvas draw execution, and `requestAnimationFrame`/`cancelAnimationFrame` all injected (real defaults, fake implementations in tests) — covering the empty state, the list's per-row content and validity/anim labeling, canvas sizing, selection highlighting, and graceful degradation (every reference reads as unresolved rather than the screen hanging on "Decoding sprites…" forever) when the WASM module itself fails to start rather than reporting a module-level parse error. Playback-specific coverage uses a fake, manually-fired `requestAnimationFrame` (queues the callback instead of scheduling it for real) to drive ticks deterministically: the Play/Pause control's own label, one batched `resolveAnimationFrames` call per tick while playing, no further calls once paused, elapsed playback position surviving a pause/resume cycle instead of resetting, and a previous stage's playback loop being cancelled (via a `WeakMap`-keyed registry) when the render function is called again on the same root element. `getContext("2d")` is real jsdom behavior returning `null` under this project's pinned jsdom (no `canvas` npm package installed) — `defaultDrawComposition` degrades to a no-op rather than throwing, and the actual pixel output is verified separately by the real-browser pass below, not asserted in these tests.

A dedicated block (backlog item 013) covers the canvas actually resizing to the real content bounding box: an element or declared `cameraBounds`/`stageBoundaries` positioned past the local coordinate window grows the canvas and keeps its `<wuik-viewport>` container's aspect-ratio in sync; out-of-order `cameraBounds`/`stageBoundaries` fields never collapse it to a negative/inverted size; a 3D (`hasModelLayer`) stage stays at the fixed window even when its 2D elements are positioned far past it; and the viewport's `resetToFit()` — spied on the actual DOM element, since it's a duck-typed method this project's pinned jsdom never implements on a plain `HTMLElement` — is re-invoked once on load, stays untouched across a playback tick whose visible extent doesn't change, and fires again only once a tick's recomputed extent genuinely grows.

## Real-stage-corpus rendering sanity test

`background-composition.corpus.test.ts` is the one test in this suite that runs the **full real pipeline** (`stage.wasm` → `sff.wasm` → `buildDrawPlan`) against a local, machine-specific corpus of real, unmodified stage folders, gated on the `STAGE_CORPUS_DIR` env var — unset ⇒ the whole `describe` block is skipped, so it never runs in CI or on another machine:

```sh
STAGE_CORPUS_DIR=~/workspace/ikemen-quick-versus/stages npm test
```

This mirrors the sibling `stage` repo's own `STAGE_CORPUS_DIR`-gated `TestCorpusCompat_RealDefFiles_ParseSuccessRate` (see its `.vibe/fixture-sources.md`), but proves a different thing: `stage`'s scan only proves a `.def` file *parses*; this one proves the *parsed result renders sensibly*. That distinction matters because a file can do the former while failing the latter — `Dengeki_Subway.def` parsed cleanly while its composed preview showed one grossly oversized, mostly off-canvas fragment, because `[StageInfo]`'s `xscale`/`yscale` (backlog item 009) wasn't applied in composition. Nothing else in this suite (all hand-picked or synthetic fixtures) would have caught that; nothing would catch the next bug shaped like it either, without a test that walks real content.

For each stage in the corpus, the test loads its `.def` and referenced `.sff` through the same real WASM bridges the fixture-driven tests above use, then runs the result through the real, pure `buildDrawPlan` composition logic (no canvas/DOM involved). A stage is flagged, by name, when either:

- its *resolved* `localCoordWidth`/`localCoordHeight` (`resolveLocalCoordSize` — backlog item 016) is zero in either dimension. `stage`'s Go parser leaves these fields at the zero value when a `.def` `[StageInfo]` section omits `localcoord` entirely, rather than falling back to MUGEN's own `320x240` default; before backlog item 016's fix, trusting that raw zero collapsed the whole composed preview to a literal 0x0 canvas. This check now runs against the same resolved size the real app renders with, so a `.def` genuinely omitting `localcoord` no longer trips it — only a value still degenerate *after* the fallback would, or
- a `"normal"`/`"parallax"`/`"anim"` element that resolves to a real (not broken/unresolved) sprite has computed draw bounds that are simultaneously **oversized** (drawn width or height exceeds `3.5x` the stage's own local coordinate space) **and** **offscreen at rest** (extends more than `0.25x` past the local coordinate rectangle on either axis).

Neither condition alone is unusual in legitimate real content — a background layer wider than the visible screen, or a parallax layer parked off-canvas ready to scroll into view, are both normal. The two together is the actual signature of a broken scale factor, since a missing scale multiplies an element's position *and* its size by the same erroneous amount. See `.vibe/decisions/007-corpus-rendering-sanity-thresholds.md` for the full numbers-backed derivation of both thresholds against the real 58-file local corpus — including the two real files (`Church Beach.def`'s floor sprite, `Otherworldly Forest.def`'s cloud parallax layer) that a single-condition threshold would have false-positived on. `isDrawBoundsNonsensical`/`isLocalCoordDegenerate` are unit-tested directly (in the same file) against fixture `DrawCommand` values reproducing both the historical bug and these legitimate real-corpus shapes, independently of the corpus scan itself.

A stage that fails a real parse, or whose referenced sprite sheet can't be found/loaded, is **skipped** rather than failed — that class of failure is `stage`'s own corpus scan's concern, not this one's, which only judges a *successfully parsed* stage's rendering. The scan logs a one-line summary (`checked`/`skipped`/`failed` counts) plus the skip reasons and, for any failure, the offending element's name, computed bounds, and the stage's own local coordinate space — the same "report failing file paths, not just a count" approach `stage`'s own corpus scan uses, so a future regression is actionable without re-deriving which file broke.

**Latest local run** (2026-09-10, 58 `.def` files, `Dengeki_Subway` fix from backlog item 009 already applied, before backlog item 016's fallback fix): 58 checked, 0 skipped, 7 failed — all 7 on the zero-`localcoord` condition above (`CC_BEACH`, `EXShadowPokemonGym`, `JB Jungle`, `School`, `XX'CC'SCHOOLYARD'XX`, `XX'GARAGE'XX`, `xxcolonyxx`), none on the oversized+offscreen condition. `Dengeki_Subway` itself passes clean, confirming this scan does flag the historical bug's reproduction (verified via the unit tests above) and no longer flags the real fixed file. Backlog item 016 fixed the underlying zero-`localcoord` rendering bug (`resolveLocalCoordSize`'s `320x240` fallback) and updated this scan's own check to judge the resolved size, so all 7 files above no longer fail this condition on a re-run against the same corpus.

A further block (backlog item 014) covers the "overview"/"game window" view toggle: it's rendered (defaulting to "overview") for a 2D stage and absent entirely for a 3D (`hasModelLayer`) stage, which always keeps the fixed local-coordinate-space window; switching to "game window" resizes the canvas to that exact fixed window and draws the untranslated plan `buildDrawPlan` alone would have produced (no bounding-box offset); switching back to "overview" re-expands it; re-selecting the already-active mode is a no-op (no extra redraw); and toggling mode while Play is running, in both directions, keeps playback running with the Play/Pause control unaffected. The toggle's own labels re-translate in place on a live locale change, the same pattern every other text in this screen already follows.

## Visual regression tests

Real browser rendering (composed background pixels, 3D model rendering) is checked with Playwright's screenshot comparison (`toHaveScreenshot()`), not the Vitest suite above — this is a separate suite/command from `npm test`, extending `web-ui-kit`'s shared visual-testing preset (`@openkakutou/web-ui-kit/testing/visual-preset`, see that repo's own `docs/testing.md`) for a fixed viewport, pinned locale, and default diff threshold, plus a helper that forces animations/transitions off and waits for fonts before a screenshot is taken.

```sh
npm run test:visual           # compares against the committed baselines
npm run test:visual:update    # regenerates baselines after a deliberate visual change
```

`playwright.config.ts`'s `webServer` builds and serves the app itself (`npm run build && npm run preview`) — `npm run test:visual` needs no separate manual build step first. `tests/visual/background-preview.visual.spec.ts` drives the app through its real `<input webkitdirectory>` folder picker (`page.locator("#stage-folder-picker").setInputFiles(...)`, the same directory-path-accepting Playwright API the real-browser folder-input verification below already relies on), loading a real, vendored stage fixture folder end-to-end rather than bypassing the loading flow, then screenshots `.background-preview__stack` — the same composed 2D-canvas-plus-optional-3D-layer region for either kind of stage.

Two baselines, from two real, vendored fixture folders (see `tests/visual/fixtures/README.md` for exact provenance and why each is trimmed to one `.def` file):

- **`dengeki-subway/`** — a real 2D MUGEN stage whose `[StageInfo]` sets `xscale = .35`/`yscale = .35`. This is the exact stage that once exposed the composition bug backlog item 009 fixed (every sprite drawn at its raw, unscaled size); its baseline is the regression guard against that bug recurring. Verified live during this item's own development: temporarily reverting `resolveBgScale`'s effect back to `{1, 1}` made this test fail with 100% of the compared element's pixels different, and restoring the fix made it pass again — confirming the suite actually catches this exact class of regression, not just that it runs.
- **`cvs2london/`** — a real, MIT-licensed Ikemen GO 3D model-based stage with no 2D BG elements of its own (the 3D model is the entire background), exercising the model-only preview path (backlog item 006) instead.

A failing comparison attaches the actual/expected/diff images to the run (`test-results/`, gitignored). Baselines are only ever regenerated deliberately and reviewed like any other diff — never silently. This suite runs as its own step in `.github/workflows/deploy-pages.yml`, after `Build` and before the Pages deploy steps, inside Playwright's own published Docker image (`mcr.microsoft.com/playwright`, pinned by digest to this repo's exact `@playwright/test` version) rather than a bare pinned-OS runner — see `.vibe/decisions/011-visual-regression-ci-runs-in-playwrights-own-docker-image.md` for why even an OS pin (`.vibe/decisions/009`) wasn't enough. Every baseline must be regenerated through that same image, never a bare local `npm run test:visual:update`:

```sh
docker run --rm -v "$PWD:/work" -w /work --ipc=host \
  mcr.microsoft.com/playwright:v1.62.1-noble \
  bash -c "npm ci && npm run test:visual:update"
```

### Why the shared preset

Both functions (`createVisualProjectConfig`, `waitForVisualReady`) come from `@openkakutou/web-ui-kit`'s own package export rather than being reimplemented here — the same fixed viewport (1280×800), pinned `en-US` locale (a headless browser's default `navigator.language` is not guaranteed to be English), and `maxDiffPixelRatio: 0.02` diff threshold every other consuming app in this org uses. See `web-ui-kit`'s own `docs/testing.md` ("Visual regression testing" section) for the full rationale.

## 3D model-based stage preview

`model-camera.test.ts` covers the pure camera-projection/model-transform math directly (no `three`, no DOM) — including that a degenerate stage-declared `far` is compared against the *resolved* (post-fallback) `near`, not the raw declared one, since a naive implementation comparing against the raw value would silently accept an invalid range. `model-preview.test.ts` covers the `three`/DOM orchestration with the renderer, glTF/`.hdr` loaders, and `requestAnimationFrame`/`ResizeObserver` all injected — no real WebGL is available under this project's `jsdom` (confirmed: it implements no WebGL context at all), so these tests exercise control flow (mount/cleanup, the failure-banner path for a missing/ambiguous/unreadable asset, the coalesced render-on-demand gate, resize sync, context-restore) against lightweight fakes rather than real three.js objects. `model-assets.test.ts` covers the model/`.hdr` resolution the same way `stage-file-input.test.ts` covers sprite-sheet resolution (basename matching, ambiguity, read errors) — reusing `basename-resolution.ts`/`file-bytes.ts` directly.

Two small, real, hand-built fixtures back the runtime-verification steps below and were validated by actually parsing them with the real `GLTFLoader`/`HDRLoader` during development (not merely assumed well-formed): `src/viewer/testdata/model.gltf` (a minimal one-triangle glTF 2.0 file, embedded base64 buffer, no external `.bin`) and `src/viewer/testdata/environment.hdr` (a minimal 2×2-pixel, old-format flat-RGBE Radiance `.hdr`).

## Localization (i18n)

`src/i18n/i18n.ts`'s `t(key, defaultValue, vars?)` returns `defaultValue` (interpolated) verbatim whenever this app hasn't called `initI18n` yet in the current test process — the large majority of tests never bootstrap i18n at all and keep asserting plain English text unchanged. Tests that specifically cover translation/live-switching (`i18n.test.ts`, and one dedicated case each in `main.test.ts`, `stage-file-input-view.test.ts`, `background-preview.test.ts`, `model-preview.test.ts`) call `initAppI18n()` themselves, then `instance.changeLanguage("fr")`, asserting the already-rendered DOM updates in place — playback/selection state (background preview) and the DOM structure of a currently-shown failure banner (3D model preview) are asserted unchanged/still-present across the switch, not just the new text.

## Loading feedback (spinner)

`stage-file-input-view.test.ts`, `background-preview.test.ts`, and `model-preview.test.ts` (backlog item 015) each assert a `<wuik-spinner>` (`@openkakutou/web-ui-kit`) is visible for the duration of that screen's own async operation — reading/parsing the `.def`, decoding the background's sprites, loading the 3D model/environment — and hidden again once it resolves, as a sibling of the existing `role="status"` text rather than replacing it. `model-preview.ts` previously had no loading indicator of any kind during its `three`/glTF/`.hdr` load; this item gave it one for the first time, not just a spinner alongside pre-existing text.

## jsdom gaps worked around in tests

`scripts/download-wasm.mjs`'s `--version` flag builds a `file:` URL via `import.meta.url` to locate its own `package.json`. Under this project's jsdom test environment, the global `URL` constructor is jsdom's own (a different realm from Node's), and `fs/promises.readFile` rejects a `URL` instance from that other realm with "The URL must be of scheme file" even though its `href` is a correct `file:` path. The fix: resolve the path via `fileURLToPath(import.meta.url)` (given the string form of the URL, not a constructed `URL` object) before joining it with `path`, which never touches the polyfilled global `URL` at all. Real `node scripts/download-wasm.mjs --version` on the command line was unaffected either way — this only ever surfaced under the jsdom test environment.

`src/input/`'s folder-gathering (`folder-entries.ts`) reads bytes via `FileReader` rather than `Blob#arrayBuffer()` — this project's pinned jsdom version doesn't implement it, the same real-browser/jsdom parity reason every other OpenKakutou app's file input uses `FileReader` instead. jsdom also doesn't implement the non-standard `FileSystemEntry`/`DataTransferItem.webkitGetAsEntry()` APIs the drag-and-drop path uses at all, so `folder-entries.test.ts` exercises that walk against plain mock objects (`FileEntryLike`/`DirectoryEntryLike`) rather than real browser objects — real drag-and-drop is instead confirmed in the real-browser pass below. Clicking a candidate-selection radio button in `stage-file-input-view.test.ts` reads the selection from a `"click"` listener rather than `"change"` — this project's pinned jsdom does toggle `.checked` on `.click()`/a dispatched `"click"` event but doesn't reliably follow it with a `"change"` event, the same workaround `character-viewer-web`'s animation player and `lifebar-viewer-web`'s own folder input use.

## Beyond the test suite: real-browser verification

Passing tests are not treated as proof the UI renders correctly. The app shell was additionally driven against a real headless Chromium (dev server + Playwright) during development: confirming the toolbar renders with `web-ui-kit`'s actual computed styles (not unstyled fallback text), that no sidebar slot is rendered, and that `stage.wasm` is not fetched just from loading the page — the bridge only ever runs on demand, once something calls `loadStage`, not eagerly at import time. For the folder input specifically, the same real-browser pass drove an actual `<input webkitdirectory>` selection against a real folder on disk (Playwright's `setInputFiles` accepts a directory path directly) — not just simulated `FileList`/entry mocks — confirming the real WASM-backed load, the real sprite-sheet resolution, the named missing-file error state, and the reset action all work end-to-end. For the characteristics panel (backlog item 003), the same real-browser pass loaded a real stage folder (a `.def` with a real `[Info]` section plus a real `.sff` sprite sheet) end-to-end and confirmed the rendered name, author, camera bounds, stage boundaries, and 2D/3D note all match the source file's actual values. For the BG element browser + background preview (backlog item 004), the same real-browser pass loaded a real stage folder with a valid, an invalid (sprite absent from the sheet), and an `"anim"`-type element together — confirming the valid sprite renders at its computed position, the invalid one shows the dashed placeholder distinctly labeled in the list, selecting a list row draws the accent-colored highlight outline over the right element, and a zero-element stage replaces the whole list+canvas layout with the empty-state message. For animated BG playback (backlog item 005), a further real-browser pass — against the real `stage.wasm` module's actual `resolveAnimationFrames` — confirmed an element with no matching animation block shows its placeholder and row label immediately, before Play is ever clicked; that clicking Play visibly pans a parallax element and cycles an animated element's sprite over real time; that Pause freezes both instantly (two screenshots roughly a second apart, pixel-identical); and that a second Play resumes motion from where it left off rather than restarting from the origin. For the 3D model-based stage preview (backlog item 006), a real-browser pass loaded a real 3D model-based stage folder (the two fixtures above, referenced from a real `.def`'s `[Model]` section) and confirmed the model actually renders (screenshotted, not just DOM presence); that dragging inside the viewport visibly changes the rendered frame (before/after screenshots differ) while an unfocused wheel event still scrolls the page normally; that a `.def` referencing a missing model file shows the distinct error banner with no `<wuik-viewport-3d>` mounted; and, as a regression check, that an ordinary 2D-only stage still renders with no 3D viewport and no mode badge at all. For localization (backlog item 008), a real-browser pass loaded a real stage folder, confirmed the toolbar's locale switcher and every screen's text render in English by default, then switched to French live from the switcher and confirmed the folder-input labels, characteristics panel field labels, and background preview's Play button/row summaries all updated immediately with no page reload and without resetting the in-progress Play/Pause state; reloading the page afterward confirmed the French choice persisted (`localStorage`); and loading an invalid folder while French was active confirmed the error message itself renders correctly translated. For overview-mode canvas sizing (backlog item 013), a real-browser pass loaded the real `dengeki-subway` fixture (whose declared stage boundaries and several elements' positions extend far past its `320×240` local coordinate window) and confirmed via the live DOM that the canvas grew well past `320×240`, its `<wuik-viewport>` container's `aspect-ratio` stayed in sync with the new size, and the whole scene (screenshotted) is visible with no clipping; that the viewport's real zoom (`+` key) and pan (arrow keys) interactions actually changed its live transform (read via the custom element's own `getTransform()`), and that resetting to fit (`Home` key) restored it; and, loading the real `cvs2london` 3D fixture, that a model-based stage with zero 2D background elements is unaffected (its 3D layer renders exactly as before, matching the pre-existing regression-tested baseline for that fixture, with no console errors in either scenario). The `hasModelLayer`-with-real-2D-elements combination — the one code path this item actually changes for a 3D stage — has no matching real vendored fixture (`cvs2london` has none), so it's covered by a dedicated unit test instead of a real-browser pass. For the overview/game-window view toggle (backlog item 014), a real-browser pass loaded the real `dengeki-subway` fixture, switched to "game window" via the real control, confirmed the canvas resized to exactly its declared `320×240` window, and screenshotted the result against a baseline extracted from this repo's own git history (the last commit before item 013's overview-mode rewiring, the exact pre-013 fixed-window rendering) — visually pixel-identical, differing only by the same 1–2px environment-rounding artifact this repo's commit history already documents between a local sandbox and the pinned CI runner, confirming this mode is a faithful reproduction rather than an approximation. A further pass confirmed the toggle is entirely absent (not just disabled) for the real `cvs2london` 3D fixture with no console errors; that toggling mode in both directions while Play was running on `dengeki-subway` kept playback going with no console errors and the Pause label unaffected; and that a live locale switch mid-playback re-translated both toggle option labels correctly while playback state was untouched. This isn't part of `npm test`; it's a manual verification step recorded in the relevant backlog item, not a CI gate. For the loading spinner (backlog item 015), a real-browser pass loading the real `dengeki-subway` (2D) and `cvs2london` (3D, model+`.hdr`) fixtures caught a bug no jsdom unit test could: `<wuik-spinner>`'s own shadow DOM unconditionally sets `:host { display: inline-block }`, which silently overrides the native `[hidden] { display: none }` UA rule, so toggling the `hidden` attribute alone had no visible effect — a jsdom test asserting the `.hidden` property itself never catches this, since jsdom doesn't compute cascaded styles. Fixed with an explicit `wuik-spinner[hidden] { display: none !important; }` rule in this app's own stylesheet, since the component itself is a published dependency, not something this repo can patch.
