# 3D model-based stage preview: three.js, render-on-demand, layered over the existing 2D canvas

**Context:** Item 006 extends the background preview (item 004) to render Ikemen GO 3D model-based stages — a glTF model, HDR image-based lighting, composited with the existing 2D BG-element canvas in one preview, driven by `web-ui-kit`'s `<wuik-viewport-3d>` (camera math only, no rendering — see that repo's `.vibe/decisions/010`). Two consulting experts (real-time rendering, frontend design) were brought in on the plan before implementation; their input shaped the decisions below.

**Decision:**
1. **`three` (0.185.x) is a new dependency** — the first 3D rendering library used anywhere in this org (no prior art to match). `GLTFLoader`/`HDRLoader` (from `three/examples/jsm/loaders/`) parse already-in-memory bytes (`.parse(...)`, never a URL fetch — both files come from the user's local folder selection, no network). `HDRLoader` is used, not `RGBELoader`: the latter is deprecated as of this three version (confirmed by a real parse warning during fixture validation), and both accept the same raw HDR bytes.
2. **Camera projection reuses the stage's own already-parsed `[Camera]`-adjacent fields** (`bgDef.fov`/`near`/`far`, already exposed by the existing WASM bridge) for the `THREE.PerspectiveCamera`, falling back to sane defaults (fov 45, near 0.1, far 10000) when a stage declares a degenerate value (≤ 0) — ties the 3D view to real stage data instead of inventing arbitrary constants.
3. **Camera *control* is render-on-demand, coalesced through a single dirty-flag + `requestAnimationFrame` gate**, not a per-event or continuous render loop — the scene is genuinely static (no animation is attempted, see decision 4). Exactly four sources mark the frame dirty: initial load-complete, `<wuik-viewport-3d>`'s `wuik-viewport3d-change` event, a `ResizeObserver` on the host (never `window.resize` — the component has no intrinsic size, per its own contract), and the WebGL `webglcontextrestored` event (a lost/restored context is a real risk even for a static scene, since render-on-demand means nothing else would ever notice a resulting black frame). A synchronous warm-up render runs immediately after setup completes, before the view is treated as ready — three.js compiles shaders/materials on first draw, so the very first user-triggered render would otherwise visibly stall.
4. **No skeletal/armature animation is played**, even if the loaded glTF declares any (`gltf.animations`) — satisfies the acceptance criterion by simply never constructing an `AnimationMixer` or calling any animation action, not by detecting and rejecting armatures.
5. **Resize keeps both canvases in sync from one `ResizeObserver` callback**: reads the host's content-box size once, applies it to the WebGL canvas (`renderer.setSize(w, h, false)`, `camera.aspect` + `updateProjectionMatrix()`) and requests one render — a 0×0 first observation (custom element inserted before layout) is guarded the same way a degenerate `fov`/`near`/`far` already is. `setPixelRatio(Math.min(devicePixelRatio, 2))` is set explicitly rather than left at the three.js default of 1, so the 3D layer isn't visibly softer than the full-DPR 2D canvas beside it.
6. **Compositing with the existing 2D BG-element canvas**: the WebGL canvas renders as the back layer; the existing, *unmodified* 2D canvas (item 004's parallax/sprite composition) is layered on top with a transparent background, `pointer-events: none`, so the 3D model shows through anywhere no sprite covers that pixel, and pointer/wheel input reaches the 3D viewport underneath uninterrupted. The 2D layer keeps its own existing fixed screen-space pixel mapping — it is **not** re-projected through the 3D camera; the two are visually stacked, not unified into one 3D-projected scene. A persistent, always-visible mode badge ("3D preview — background elements stay screen-fixed") is shown whenever this layered mode is active, so a 2D sprite visibly not responding to orbit reads as expected behavior, not as broken.
7. **The WebGL canvas's clear/fill color is re-read from `--wuik-color-surface` on every render** (never cached from mount), the same "don't bake in a first-paint value" rule the existing 2D `defaultDrawComposition` already follows — relevant even though this app has no in-app theme toggle, since the OS-level `prefers-color-scheme` can still change the resolved token live.
8. **A failed-to-resolve or failed-to-load model/`.hdr` asset renders a DOM banner** inside the 3D preview area (icon/border/heading in danger tokens, body text in the default text token) instead of any canvas drawing — there's no decoded content to outline the way the existing sprite placeholder does. Deliberately structured differently from both the existing sprite placeholder (dashed canvas outline) and `<wuik-viewport-3d>`'s own neutral "WebGL unsupported" panel, so three distinct failure causes (an unresolved sprite reference, no WebGL, a failed 3D asset) never share one visual language. Renderer/context construction failing outright (no-WebGL, driver blocklist) routes to this same banner, via its own guard separate from the asset-parse try/catch.
9. **Asset resolution (locating the referenced model/`.hdr` file in the already-gathered folder listing, by basename) is never a blocking failure for the overall stage load** — unlike the existing sprite-sheet resolution (item 002/003, a hard error), a missing/ambiguous/unreadable model or `.hdr` file only affects the 3D preview area (banner from point 8); the rest of the app (characteristics panel, 2D BG preview) loads normally. A stage with no `[Model]` data (`bgDef.modelFile === ""`) skips every code path added by this item entirely — zero DOM/canvas additions, identical output to the pre-item build.

**Reason:** Each of the above traces to a concrete requirement or risk named by the two expert consultations (frame-budget/render-loop structure from real-time rendering; layered-compositing legibility and failure-state visual language from frontend design) or to a fact confirmed by actually running the real loaders against hand-built fixtures during planning (the `RGBELoader`→`HDRLoader` deprecation) — not spec'd speculatively.

**Rejected alternatives:**
- **A continuous `requestAnimationFrame` render loop**: rejected — the scene is genuinely static except for user-driven camera changes; a per-frame render with nothing to redraw is pure waste this render-on-demand design avoids entirely.
- **Re-projecting the 2D BG elements into the 3D world as billboards, unifying both into one true 3D camera**: rejected — no acceptance criterion asks for it, and it would require solving 2D-sprite-in-3D-depth-sorting the acceptance criteria never raise; the layered-canvas composite delivers "both compose correctly in one preview" without that added complexity.
- **`RGBELoader`**: rejected once its own deprecation notice was observed firsthand while validating fixtures — `HDRLoader` is the direct, API-compatible replacement in this three.js version.
- **Reusing the sprite placeholder's dashed-outline visual language for a failed 3D asset**: rejected per the frontend-design consultation — conflates "one sprite unresolved" with "the whole 3D layer failed to load," a materially different failure a user needs to distinguish at a glance.
