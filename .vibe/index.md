# stage-viewer-web — Codebase index

## Modules
- [`modules/app.md`](modules/app.md) — application entry point, builds the app's `web-ui-kit` root frame (toolbar + the stage file input as main content), wires a successful load to the characteristics panel and the BG element browser + background preview, and mounts it into the DOM
- [`modules/input.md`](modules/input.md) — the stage folder input: gathers files from a folder selection/drag-and-drop, picks the `.def` candidate, loads it via the WASM bridge, and resolves its referenced sprite sheet from the same folder by basename; also renders the folder-picker/drag-and-drop UI
- [`modules/wasm.md`](modules/wasm.md) — bridge to the `stage` WASM module: loads it client-side and exposes typed `loadStage`/`resolveAnimationFrames` wrappers, plus the `StageData` TypeScript vocabulary, each returning a typed result instead of throwing
- [`modules/sff-wasm.md`](modules/sff-wasm.md) — a second, independent bridge to the `sff` WASM module: sprite metadata and pixel decode, used to place and validate a BG element's sprite reference
- [`modules/viewer.md`](modules/viewer.md) — the screens that show what was loaded: the characteristics panel, and the BG element browser + composed background preview (canvas, wrapped in `web-ui-kit`'s viewport control) with time-based Play/Pause playback
- [`modules/scripts.md`](modules/scripts.md) — dev-tooling scripts, e.g. downloading the `stage` and `sff` WASM release builds

## Observed patterns
- The DOM-building logic of a screen/component is a pure exported function (`renderApp(root, version, options?)`, `renderStageFileInput(root, options)`) taking its target element and data/callbacks as parameters, kept separate from the module-level bootstrap — same "inject external effects for testability" shape as the WASM bridge and download script, applied here to DOM construction instead of `fetch`
- Any app-level visual value (typography hierarchy, spacing) is expressed only through `@openkakutou/web-ui-kit`'s `--wuik-*` CSS custom properties, never a literal px/hex value
- TypeScript with `strict`, `noUnusedLocals`, `noUnusedParameters` enabled (`tsconfig.json`)
- Explicit `.ts` extensions on relative imports (`allowImportingTsExtensions`)
- Test files co-located with source as `*.test.ts`/`*.test.mjs`, using Vitest + jsdom
- Dev-tooling scripts outside the app bundle live in `scripts/` as plain `.mjs` (not bundled/type-checked by `tsc`, whose `include` is scoped to `src/`)
- CLI-style scripts return an exit code from a testable `main(argv, overrides)` function rather than calling `process.exit` directly, and inject external effects (`fetch`, output dir) as parameters for testability — the same shape reappears in `src/wasm/bridge.ts` (`fetchWasmExecSource`/`fetchWasmBytes`) and `src/input/stage-file-input.ts` (`readFileBytes`/`loadStage`)
- `wasm_exec.js` (a plain global-side-effect script, not an ES module) is executed via `new Function(source)()` rather than a `<script>` tag or dynamic `import()`, so the same loading code works identically in a real browser and under jsdom/Node
- A WHATWG `URL` object is never constructed from `import.meta.url` when the result feeds a Node `fs` call — jsdom's global `URL` is a different realm from Node's own, and `fs`'s functions reject a cross-realm `URL` instance even with a correct `file:` href; `fileURLToPath(import.meta.url)` (given the string form) sidesteps this
- A field whose Go source is a nil-by-default slice is typed as `T[] | null` in TypeScript, not `T[]` — matches `encoding/json`'s actual nil-slice-marshals-to-`null` behavior instead of assuming an empty array
- A referenced filename that a real-world text format writes inconsistently (directory prefix, separator style, letter case) is resolved by basename, exact match first, case-insensitive fallback second, rather than a byte-for-byte string comparison — backed by real-corpus evidence from a sibling repo (`character`'s own `.vibe/backlog/done/050-...case-sensitively.md`), not assumed; more than one match is reported as ambiguous rather than silently picked
- File bytes are read via `FileReader` rather than `Blob#arrayBuffer()` — this project's pinned jsdom doesn't implement the latter, the same real-browser/jsdom parity reason every OpenKakutou app's file input uses `FileReader` instead
- Non-standard browser APIs jsdom doesn't implement at all (`FileSystemEntry`, `DataTransferItem.webkitGetAsEntry()`) are modeled as minimal `*Like` interfaces (only the members actually used) so the drag-and-drop walk logic is unit-testable against plain mock objects, with the real browser behavior confirmed separately via real-browser verification
- Clicking a radio input in a test is read via a `"click"` listener, not `"change"` — this project's pinned jsdom doesn't reliably synthesize `"change"` after a dispatched `"click"`
- Fixture-driven tests that exercise the real WASM module pin expected values obtained by running the actual module once against the fixture (not derived from the same mapping code under test), copying a minimal `.def` fixture from the `stage` repo's own test data into `src/wasm/testdata/` rather than depending on a sibling checkout at test time
- Real-browser verification of a file-input feature drives an actual `<input webkitdirectory>` selection against a real folder on disk (Playwright's `setInputFiles` accepts a directory path directly) rather than only simulated `FileList`/entry mocks
- A field the underlying format leaves optional (e.g. a stage's name/author) renders as the literal text "Unknown" when empty, treated as a normal value rather than a visually distinct one — keeps it scannable and matches acceptance criteria that forbid a blank/broken-looking section
- A derived fact about loaded data that a raw numeric field could be mistaken for evidence of (e.g. "is this a 3D stage") is computed from the field that actually carries that meaning (`bgDef.modelFile`'s emptiness) and stated explicitly in the UI, never inferred from another field's value being zero
- Pure composition/positioning math (coordinate mapping, draw order, placeholder sizing) lives in its own module with no DOM/canvas/WASM dependency, fully unit-testable on its own; the DOM/canvas orchestration on top is a separate module/file
- Two Go WASM modules from different producer repos are bridged independently rather than one being taught the other's surface, when the second module already ships the exact capability needed (`sff`'s own sprite metadata/pixel decode) and the first's own backlog item for it would add unrelated or insufficient capability — each module's release assets (including its own `wasm_exec.js`) download into a separate subdirectory so the two never collide, since a `wasm_exec.js` is only guaranteed compatible with the Go toolchain version that built its own paired `.wasm` binary
- A canvas-drawn element resolving to the underlying library's own "nothing to draw this frame" sentinel (a legitimately empty/degenerate state, not an error) is simply not drawn at all — no placeholder, no error styling — kept visually and semantically distinct from a reference that genuinely fails to resolve (no matching config, or resolves outside the sprite sheet), which does get a placeholder; the two must never share a visual treatment
- A canvas 2D color is resolved via `getComputedStyle` at draw time, never read once and cached, so it stays correct across a theme switch — the same "don't bake in a first-paint value" concern the color-token system requires everywhere else
- `getContext("2d")` returning `null` (a real, if rare, browser condition, and this project's pinned jsdom without the `canvas` npm package) is a guarded no-op in the draw function, never a thrown exception; the real pixel output is verified by a real-browser pass, never asserted in a jsdom test
- A DOM/canvas component whose real async dependency (a WASM bridge call) can reject, not just resolve with a typed error, degrades the same way a fully-failed/empty result would (`.catch()` normalizes to the same "finish" path) rather than leaving the UI stuck on a loading state or producing an unhandled rejection
- A `requestAnimationFrame`-driven playback clock advances state from real elapsed time between callback timestamps (clamped to a maximum per-step delta), never by counting callbacks — keeps playback speed correct regardless of refresh rate and bounds the jump after a backgrounded/throttled tab resumes; both `requestAnimationFrame`/`cancelAnimationFrame` are injectable options, defaulting to the real globals, for deterministic tests
- A render function that can start a background loop (e.g. a `requestAnimationFrame` chain) registers a stop callback for its root element in a module-level `WeakMap<rootElement, stopFn>`, called and cleared at the top of the next call on that same root — prevents a previous call's loop from continuing to run invisibly once new content replaces it
- A per-tick async resolution (e.g. a batched WASM call) that fails (rejects, or returns a typed error) leaves the previously-resolved state untouched rather than clearing it, so one transient failure doesn't flash already-working content to a broken state; the tick still redraws with whatever was already known
- A tick handler `await`s its async resolution before drawing and before scheduling the next frame, rather than firing-and-forgetting with a re-entrancy guard that skips a busy tick — keeps every value redrawn together from the same tick instead of some advancing (e.g. a driven-by-local-state camera) while others (a WASM-resolved value) lag
